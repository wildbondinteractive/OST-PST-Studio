# Code signing policy

This is the code signing policy for OST/PST Studio, published under the Wildbond
Interactive name (file and product name "OST-PST Studio", because a slash cannot appear
in a Windows file name). It is linked from the README and from every release page.

## Status

| Release | Signed | Notes |
|---|---|---|
| 0.1.0, 0.1.1 | No | Built by the public workflow, unsigned. Windows SmartScreen warns on first run. |
| 0.1.2 and later | Yes, once the first verified signed release is published | Signed through Microsoft Azure Artifact Signing by the release workflow; every file is verified before it can be published. |

No release is described as signed until a release built by the signing workflow has
been published and its signatures have verified on a machine other than the one that
built it. Until then, every published binary is unsigned and says so on its release
page. Release notes and this table are updated together.

## How releases are signed

Releases are signed with **Microsoft Azure Artifact Signing**, a managed signing
service, using a **Public Trust** certificate profile. The signatures are standard
Windows **Authenticode** signatures:

- **Publisher.** The certificate names the verified identity of the project's
  maintainer, an individual, as validated by Microsoft. Windows shows that name as the
  publisher in the signature details and in the User Account Control prompt. "Wildbond
  Interactive" is the project's branding; it is not the certificate subject, and nothing
  in this project presents it as one.
- **Certificate.** Issued by Microsoft's public trust certification authority under the
  Microsoft Identity Verification Root Certificate Authority 2020, which Windows trusts
  out of the box. Each signing certificate is short-lived (hours to days) and is
  generated by the service for the signing operation; the private key exists only inside
  the service's hardware security modules. No certificate file or key is ever exported,
  downloaded, or stored by the project.
- **Digest and timestamp.** Files are signed with a SHA-256 digest and timestamped by
  Microsoft's RFC 3161 timestamp service (`http://timestamp.acs.microsoft.com`) with a
  SHA-256 timestamp digest. The timestamp is what keeps a signature valid after the
  short-lived certificate expires, so it is mandatory and the workflow fails without it.
- **What is signed.** The desktop executable (`ostpst-studio.exe`, also published as the
  portable build), the command-line executable (`ostpst.exe`), the NSIS installer, the
  uninstaller it carries, and the MSI installer. The installer builder signs the
  executable at the moment it packages it, so the program inside each installer is
  signed, not only the wrapper; each installer is then signed as a whole. The NSIS
  plug-in libraries the installer embeds and the WiX tooling the MSI is built with are
  third-party components and are not signed under this project's identity; the
  installer's own signature covers everything it contains.
- **Why the executable inside an installer differs from the portable one.** The
  installer builder writes a short marker into the executable saying which kind of
  installer it came from (used to find the matching uninstaller). The portable build
  carries the plain marker. Each variant is signed separately and each signature is
  valid for its file; the three are the same program.

## How releases are built

1. All source lives in this repository. The engine is derived from pstfree (MIT), carried
   in `crates/ostpst-core` with upstream attribution on every carried-over file. No
   pre-built third-party binary is included.
2. The continuous-integration workflow (`.github/workflows/ci.yml`) runs on every push
   and pull request on a GitHub-hosted Windows runner: formatting, clippy, the full test
   suite against the public fixtures, the TypeScript check, the Tauri bundle and an
   independent read of the conversion output with libpff. It signs nothing.
3. A release is cut by pushing a version tag (`v1.2.3`, or `v1.2.3-rc.N` for a
   pre-release) that matches the version in `Cargo.toml`, `package.json` and
   `src-tauri/tauri.conf.json`. The release workflow (`.github/workflows/release.yml`)
   refuses any other ref.
4. The release workflow builds from that tag on a GitHub-hosted Windows runner, runs the
   tests, builds the installers with signing hooked into the installer builder (the
   executable is signed as each installer packages it, then the installer is signed),
   signs the portable executable and the command-line tool, verifies every file
   (including the executable unpacked from inside each installer), writes
   `SHA256SUMS.txt`, and attaches the set to a **draft** GitHub Release. A maintainer
   publishes the draft by hand after looking at it.
5. There is no unsigned path through that workflow. If signing or verification fails,
   the run fails and nothing is attached to a release. Nothing built on a developer's
   machine is ever published as a release.

## Access control

- Signing can only happen inside the GitHub Actions environment `release-signing`, which
  is restricted to version tags. Pull requests and branch builds cannot reach it.
- The workflow authenticates to Azure with OpenID Connect (workload identity
  federation): GitHub issues a short-lived token for the specific run, which Microsoft
  Entra ID exchanges for a short-lived Azure credential. There is no client secret, no
  password, no personal access token and no key in the repository or in GitHub.
- The Entra application used by the workflow holds one Azure role, Artifact Signing
  Certificate Profile Signer, on the signing account. It cannot manage the account,
  the certificate profile, or anything else in the subscription.
- The repository owner is the only person who can push tags, change the workflow, or
  change the environment's variables, and uses two-factor authentication on GitHub and
  multi-factor authentication on Azure.

| Role | Who |
|---|---|
| Maintainer, committer, release approver | Jacob Adlon, GitHub [@wildbondinteractive](https://github.com/wildbondinteractive), repository owner |

Changes to `.github/workflows/`, `scripts/`, `src-tauri/tauri.conf.json` and the
`Cargo.toml` files are treated as changes to the release process and reviewed as such.

## Verifying a download

Every release page lists the SHA-256 of each file. On the file you downloaded:

```powershell
Get-FileHash ".\OST-PST Studio_0.1.2_x64-setup.exe" -Algorithm SHA256
Get-AuthenticodeSignature ".\OST-PST Studio_0.1.2_x64-setup.exe" | Format-List Status, SignerCertificate, TimeStamperCertificate
```

`Status` must read `Valid`, the signer's subject must name the publisher, and a
timestamper certificate must be present. In File Explorer the same information is under
Properties, Digital Signatures. The script that the release workflow runs,
[scripts/verify-signatures.ps1](../scripts/verify-signatures.ps1), performs the full
set of checks on a downloaded file, including the executable inside an installer:

```powershell
.\scripts\verify-signatures.ps1 -Path "$env:USERPROFILE\Downloads\OST-PST Studio_0.1.2_x64-setup.exe" -Embedded
```

## SmartScreen

A valid signature identifies the publisher and proves the file was not altered. It does
not by itself stop Microsoft SmartScreen from warning: SmartScreen also weighs how many
people have run a given publisher's files before. A new project with a valid signature
can still see "Windows protected your PC" until that reputation has accumulated. That is
expected, it is not a sign that the file is wrong, and this project does not claim
signing removes it.

## What the software does with your data

OST/PST Studio processes mailboxes entirely on the user's computer, makes no network
connections, collects no telemetry and contains no update check. The one network action
is the installer fetching Microsoft's WebView2 runtime when it is absent from the PC.
The full statement is in [docs/PRIVACY_POLICY.md](PRIVACY_POLICY.md); third-party
components are listed in [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md).

## Installation and removal

The NSIS installer installs for the current user and registers an entry under Settings,
Apps, Installed apps, from which it is removed; the MSI does the same through Programs
and Features. The portable executable needs no installation and is removed by deleting
it. Both leave behind the preferences and history files described in the privacy
policy, which can be deleted from the application's Settings page or by removing the
application's folder under `%APPDATA%` and `%LOCALAPPDATA%`.
